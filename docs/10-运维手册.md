# 10 · 天衡运维手册

> 面向部署与值守。所有命令均为真实可执行；配置项与 `src/internal/config/config.go` 逐条对齐（核对方法见 §9）。

## 1. 组件与端口

| 组件 | 默认端口 | 说明 |
|---|---|---|
| Go 网关（`src/cmd/server`） | 8080 | 数据面 `/v1/*`、管理面 `/api/*`、`/healthz`、`/metrics` |
| Next.js 前端（`web/`） | 3000 | 通过 rewrites 把 `/api` `/v1` 反代到网关 |
| Nginx（`deploy/nginx.conf`） | 80 | SSE 必须 `proxy_buffering off` |
| 状态目录（`DATA_DIR`） | `./.tianheng-data` | JSON + WAL + 完整性链 + 头像 + 论坛 |

## 2. 部署

### 2.1 二进制直跑（最快）

```bash
cp .env.example .env      # 填入 MASTER_KEY / JWT_SECRET / ADMIN_PASSWORD
set -a && . ./.env && set +a
go build -o /usr/local/bin/tianheng ./src/cmd/server
/usr/local/bin/tianheng
curl -s localhost:8080/healthz
# {"channels":0,"discovered_models":0,"real_models":460,"real_models_source":"data/models-real.json","status":"ok","users":0}
```

### 2.2 Docker Compose

```bash
cd deploy
cp ../.env.example .env   # 至少填 MASTER_KEY / JWT_SECRET / ADMIN_PASSWORD
docker compose up -d --build
docker compose ps
curl -s localhost/healthz
```

`deploy/docker-compose.yml` 的 `app` 服务以只读挂载 `data/`，状态写入命名卷 `app-state`；`nginx` 依赖 `app` 的 healthcheck。

### 2.3 前端

```bash
cd web
LLM_HUB_BACKEND_ORIGIN=http://127.0.0.1:8080 npm run build
LLM_HUB_BACKEND_ORIGIN=http://127.0.0.1:8080 npm start -- -p 3000
```

**关键坑**：Next.js 的 `rewrites` 在 **build 时**烘焙进 `.next/routes-manifest.json`，运行期改 `LLM_HUB_BACKEND_ORIGIN` 无效。换后端地址必须带该变量重新 `npm run build`。验证：

```bash
python3 -c 'import json;print(json.load(open("web/.next/routes-manifest.json"))["rewrites"])'
```

## 3. 备份与恢复

```bash
# 备份（服务运行中亦可：快照是原子写 + fsync + rename）
tar czf "/backup/tianheng-$(date +%Y%m%d-%H%M%S).tgz" -C "$DATA_DIR" .

# 完整性自检（启动时自动执行，也可离线验证）
python3 - <<'PY'
import json,hashlib,pathlib,os
d = pathlib.Path(os.environ["DATA_DIR"])
chain = json.loads((d/"state.integrity").read_text())
print("seq =", chain.get("seq"), " rings =", len(chain.get("chain", [])))
PY

# 恢复
kill $(cat /run/tianheng.pid)
rm -rf "$DATA_DIR" && tar xzf /backup/tianheng-XXXX.tgz -C "$DATA_DIR"
chmod 700 "$DATA_DIR" && chmod 600 "$DATA_DIR"/*.json "$DATA_DIR"/state.integrity
/usr/local/bin/tianheng
```

若启动报 `*IntegrityError`，说明状态文件与完整性链不一致 —— **回滚到最近备份**，不要删除 `state.integrity`。

## 4. 密钥轮换

### 4.1 MASTER_KEY（加密上游 api_key）

```bash
NEW=$(python3 -c 'import os,base64;print(base64.b64encode(os.urandom(32)).decode())')
# 1) 双密钥并存启动
MASTER_KEY_PREVIOUS="$OLD" MASTER_KEY="$NEW" ./tianheng
# 2) 逐渠道重加密：对每个渠道 PUT 一次（提交同一 api_key）
for id in $(curl -s -H "Authorization: Bearer $JWT" localhost:8080/api/channels | python3 -c 'import sys,json;print(" ".join(c["id"] for c in json.load(sys.stdin)["data"]))'); do
  curl -s -X POST -H "Authorization: Bearer $JWT" "localhost:8080/api/channels/$id/test" >/dev/null
done
# 3) 清空 MASTER_KEY_PREVIOUS 后重启
```

### 4.2 JWT_SECRET

直接替换并重启，所有会话立即失效（期望行为）。

## 5. 攻防防火墙运维

```bash
# 只读状态（public）
curl -s localhost:8080/api/firewall/status
# {"level":"observe","sealed":false,"session_epoch":0,"blocked_ips":0,...}

# 脱敏事件（JWT）
curl -s -H "Authorization: Bearer $JWT" "localhost:8080/api/firewall/events?limit=20"

# 自检（public）：凭据泄露与哈希链
curl -s localhost:8080/api/firewall/verify
# {"verified":true,"credential_leaks":0,"hash_chain_intact":true,...}

# 解锁 / 封存（JWT + 仅本机回环）
curl -s -X POST -H "Authorization: Bearer $JWT" localhost:8080/api/firewall/unlock
curl -s -X POST -H "Authorization: Bearer $JWT" "localhost:8080/api/firewall/seal?reason=drill"
```

**语义要点**（对应补丁 019/020/021）：

| 场景 | 行为 |
|---|---|
| 攻击触发 lockdown | 全部业务端点 `423`，`/healthz` 与回环运维通道例外 |
| 远程尝试解锁 | `403 ops_loopback_only`（V-36：防攻击者把保护变成 DoS 开关） |
| 封存期间登录 | 远程 `423`；**回环** `200`（V-38：防自锁） |
| 冷却到期 | `level` 自动降级，但 `sealed` 必须显式解锁 |
| SSE 并发 | 上限 256（`TELEMETRY_STREAM_MAX_CONNS`），超出 `503` |

## 5.5 路由原理运行时视图（Magpie 原理原生实现）

天衡在内部原生实现了 AI 供应商聚合层的五条路由原理（详见 `docs/20-Magpie原理原生实现.md`）：
会话亲和（复用上游 prompt 缓存）、分组 + 条件规则、三级出站脱敏、上下文构成分解、路由决策全量留痕。

```bash
# 会话亲和：哪些会话钉在哪个上游、缓存命中率多少
curl -s localhost:8080/api/routing/affinity

# 决策日志：某天的记录 + 真实汇总（失败切换次数/P95/脱敏总数）
curl -s "localhost:8080/api/routing/journal?summary=1"
curl -s "localhost:8080/api/routing/journal?day=2026-11-08&limit=5"

# 分组与规则：逻辑名 → 多上游成员；可预演规则命中
curl -s localhost:8080/api/routing/groups
curl -s "localhost:8080/api/routing/resolve?model=liquid/lfm-3-1.7b&effort=high&images=1"

# 脱敏策略与预演（出站遮蔽 + 入站还原）
curl -s localhost:8080/api/routing/redact
curl -s -X POST -H 'Content-Type: application/json' \
  -d '{"text":"用 sk-xxx 连 10.0.0.1，家目录 /Users/me/app"}' \
  localhost:8080/api/routing/redact/preview
```

落盘位置与权限：`$DATA_DIR/affinity.json`（0600）、`$DATA_DIR/groups.json`（0600）、
`$DATA_DIR/routing/YYYY-MM-DD.jsonl`（0600，目录 0700，历史自动 gzip）、
`$DATA_DIR/masking/YYYY-MM-DD.jsonl`（0600，只写计数不含原文）。

## 7. 故障排查

| 现象 | 原因 | 处置 |
|---|---|---|
| 启动即退出，日志含 `MASTER_KEY 未配置` | 未注入主密钥（补丁 002 拒绝回退开发密钥） | 注入 32 字节 base64 `MASTER_KEY` |
| 启动报 `*IntegrityError` | 状态文件被篡改或与链不一致 | 回滚备份；不要删 `state.integrity` |
| 全部业务 423 | 防火墙 lockdown 封存中 | 本机 `POST /api/firewall/unlock` |
| 远程 unlock 403 | V-36 修复后的预期行为 | 到本机（回环）执行 |
| 前端 `/api/*` 返回 404（Next 的 404 页） | `LLM_HUB_BACKEND_ORIGIN` 未在 build 时生效 | 带该 env 重新 `npm run build` 再 `npm start` |
| SSE 不逐块输出 | 反向代理缓冲 | Nginx 设 `proxy_buffering off` + `X-Accel-Buffering: no` |
| **页面"变了个样子"／全站无样式** | **在运行中的 next-server 之上替换了 `.next`**：旧进程继续输出引用旧哈希资源的 HTML，而这些文件已被新构建删除 → CSS/JS 全 404，页面退化成裸 HTML | 用 `bash deploy/web-restart.sh`（先停旧进程再按当前构建启动）；诊断用 `bash verify/web_assets_check.sh`（会直接指出「进程启动早于构建」） |
| 页面字体与设计稿不同 | `fonts.googleapis.com` 不可达（离线/内网）→ Plus Jakarta Sans 回退到系统字体栈 | 属预期降级（`--font-sans` 已含 `ui-sans-serif/system-ui/PingFang SC/Microsoft YaHei`）；需像素级一致时把 woff2 放 `web/public/fonts/` 并加 `@font-face` |
| 本机联调时创建渠道报 `base_uri 校验失败: 拒绝内网/回环` | SSRF 防护正确工作（默认拒绝 127/8、RFC1918、169.254 元数据） | 本机开发/靶场设 `ALLOW_PRIVATE_UPSTREAM=1`；**生产绝不要设** |
| 想确认路由为什么选了某个上游 | 决策日志有 `order[]`（候选排序 + 命中依据）与 `tries[]`（每次尝试状态/耗时） | `curl -s localhost:8080/api/routing/journal?limit=1` |
| 想知道多轮对话是否复用上游缓存 | 亲和统计有真实缓存命中率 | `curl -s localhost:8080/api/routing/affinity` |
| 启动脚本报 `XXX: unbound variable` 且变量名后是中文 | macOS 自带 bash 3.2 把紧跟 `$VAR` 的多字节 UTF-8 字节并入变量名 | 写 `${VAR}` 显式界定；本仓 `deploy/*.sh`、`verify/*.sh` 已统一 |
| `/v1/chat/completions` 502 `upstream_error` | 无可用上游渠道 | 到 `/channels` 贡献渠道（填 base_uri + api_key，模型自动发现） |
| 渠道 `models_discovered=0` + `probe_status=unavailable` | 上游 `GET /models` 拉取失败 | 检查 `base_uri`/`api_key`/出网；**系统不会编造模型** |
| 上传头像 413 | 超过 2 MiB | 压缩后重传 |
| 上传头像 400 | 魔数/类型不符 | 仅 PNG/JPEG/WebP/GIF |

## 9. 配置核对

```bash
grep -oE '(get[a-z]+|randomSecret|envInt)\("[A-Z_0-9]+"' src/internal/config/config.go src/internal/firewall/firewall.go \
  | grep -oE '"[A-Z][A-Z_0-9]+"' | tr -d '"' | sort -u > /tmp/keys.txt
grep -rhoE 'os\.Getenv\("[A-Z_0-9]+"\)' src/ | sed 's/.*("//;s/")$//' | sort -u >> /tmp/keys.txt
sort -u /tmp/keys.txt -o /tmp/keys.txt
grep -oE '^[A-Z][A-Z_0-9]+=' .env.example | sed 's/=$//' | sort -u > /tmp/tpl.txt
comm -23 /tmp/keys.txt /tmp/tpl.txt   # 必须为空
```
