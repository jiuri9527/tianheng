## 1. 基线问题（加固前）

| # | 加固前实现 | 风险 |
|---|---|---|
| 1 | `Save()` 用 `os.WriteFile(tmp, data, 0600)` + `os.Rename` | 无 `File.Sync()`、无目录 `fsync`；崩溃/掉电可能留下半截文件；临时文件名固定 `.{name}.tmp`，并发/崩溃残留会互相踩踏 |
| 2 | 旧目录用 `os.MkdirAll(dir, 0700)`，但既有文件权限从不被收紧 | 数据文件（含渠道 `api_key` 密文、完整请求日志）可能被宽松 umask 或历史文件保留为 0644 |
| 3 | 磁盘上无任何完整性元数据 | 任何进程篡改 `users.json` / 删除 `tokens.json` 后 `New()` 静默加载，无法区分「合法写入」与「篡改」 |
| 4 | 无 WAL | 多表写入中途崩溃 → 10 张表版本不一致；无恢复手段 |
| 5 | 无备份 | 无回滚点 |
| 6 | `Save()` 只取 `s.mu.RLock()` | 两个并发 `Save()` 可同时持有读锁并交错写同一批文件；`api/server.go`、`channels_api.go`、`tokens_api.go`、`auth_api.go` 及 firewall 的 `OnLockdown/OnRecover` 都会调用 `Save()` |

## 2. 加固算法

新增实现全部位于 `src/internal/store/hardening.go`（约 30 KB，仅标准库：`crypto/sha256`、`encoding/{base64,hex,json}`、`errors`、`fmt`、`os`、`path/filepath`、`sort`、`strconv`、`strings`、`time`）。

### 2.1 原子写与权限（需求 1）

`atomicWriteFile(path, data)`：

```
os.CreateTemp(dir, ".tmp-"+base+"-*")   // 唯一临时名，O_EXCL，默认 0600
  → f.Chmod(0600)                        // 显式收紧，忽略 umask
  → f.Write(data)
  → f.Sync()                             // 文件数据 fsync
  → f.Close()
  → os.Rename(tmp, path)                 // 原子替换
  → syncDir(dir)                         // 打开目录 fd + d.Sync()，落盘目录项
```

- 任何一步失败立即返回 error，`defer os.Remove(tmp)` 清理；`rename` 成功后才 fsync 目录。
- `ensureLayout()`：`os.MkdirAll(dir, 0700)` + `os.Chmod(dir, 0700)`；`backups/` 同 0700；启动时清理 `.tmp-*` 残留；`HardenPermissions()` 把 10 张表、`state.integrity`、`wal.log`、全部备份文件强制 `chmod 0600`。
- 实测 macOS/APFS 上目录 `Sync()` 返回 `nil`（`(d, _ := os.Open(dir); d.Sync())` 已验证），因此 `syncDir` 严格返回错误，不做静默降级。

### 2.2 SHA-256 完整性链（需求 2）

`state.integrity` 是带自身校验和的清单：

```json
{
  "version": 2,
  "sequence": 8,
  "state_hash": "<sha256(标准快照文档)>",
  "tables": {"users":"<sha256(users.json 字节)>", ... 共 10 张表},
  "chain": [
    {"seq":1,"prev":"<genesis>","state":"...","chain":"...","time":...},
    ...
    {"seq":8,"prev":"<第7环 chain>","state":"...","chain":"...","time":...}
  ],
  "updated_at": 1794063282,
  "adopted_legacy": false,
  "checksum": "<sha256(清单除 checksum 外的确定性 JSON)>"
}
```

- **链环公式**：`chain_i = SHA256(prev_chain || "|" || state_i || "|" || seq_i)`；`prev_chain` 初始为 `genesis = SHA256("llm-hub-store-integrity-genesis-v1")`。
- **标准快照文档**：`{"tables":{表名: base64(表文件字节)}}`，`encoding/json` 对 map 键排序 → 字节确定；`state = SHA256(该文档)`。
- **每次写入**：`sequence += 1`，追加一环，`state_hash` 更新为本次快照摘要，`tables` 更新为逐表摘要，`checksum` 重算后原子写入。
- **启动时校验**（`openState` → `verifyFiles`，只读、严格）：
  1. 清单 `checksum` 自校验（防清单自身被改）；
  2. `version` 必须为 2；
  3. 逐环校验 `prev` 连续、`chain_i` 公式、`seq` 严格单调递增，链头 `seq/state` 必须等于清单 `sequence/state_hash`；
  4. 逐表读取字节算 SHA-256，与 `tables[name]` 比对；**文件缺失即报错**（删除检测）；
  5. 由实际文件重建标准快照文档，其 SHA-256 必须等于 `state_hash`。
- 任何一步不符返回 `*IntegrityError{File, Reason, Expected, Actual}`，`New()` 直接返回该错误，**绝不静默接受**。`IsIntegrityError(err)` 供调用方判定。
- 明确错误示例（真实测试输出）：
  `store 完整性校验失败 [users.json]: 状态文件 SHA-256 与 state.integrity 不一致（疑似篡改） (expected=c7a42cbe… actual=b21a22c2…)`

### 2.3 WAL / 快照与崩溃恢复（需求 3）

`wal.log` 为追加式、每行一条 JSON，字段 `seq / state / prev / snapshot / checksum / time`：

```
snapshot = base64(标准快照文档)          // 完整快照，可独立重放全部 10 张表
checksum = SHA256(seq|state|prev|snapshot)
```

`saveHardened()`（由 `Save()` 委托，签名不变）严格顺序：

```
writeMu.Lock()
  ├─ 在 s.mu.RLock() 下构建一致性快照（10 张表 MarshalIndent）
  ├─ ① appendWALRecord()：追加 + f.Sync() + syncDir()    ← 写前日志
  ├─ ② 逐表 atomicWriteFile()                            ← 10 次原子写
  ├─ ③ rotateBackups()：写快照备份 + 轮转
  ├─ ④ writeManifest()：推进完整性链，原子写 state.integrity
  └─ ⑤ truncateWAL()：提交完成，WAL 检查点清空 + syncDir()
writeMu.Unlock()
```

崩溃点覆盖：

| 崩溃位置 | 启动时行为 |
|---|---|
| ① 之前（WAL 未落） | 清单仍为旧 seq，WAL 无更新记录 → 清空 WAL → 校验旧状态通过 |
| ① 与 ④ 之间（含 ②③ 任意一步） | WAL 存在 `seq = 旧清单 seq + 1` → `recoverFromWAL()` 用 WAL 快照重写全部表、追加链环、写清单、清空 WAL |
| ④ 与 ⑤ 之间 | WAL `seq == 清单 seq` → 清空 WAL → 校验通过（幂等） |
| ⑤ 之后 | WAL 为空 → 校验通过 |
| WAL 半截行/校验和损坏 | `readWAL()` 只取有效前缀，尾部损坏视为崩溃残留丢弃；不污染已提交状态 |

`recoverFromWAL()` 还会校验：WAL 快照的 SHA-256 必须等于记录里的 `state`；WAL 的 `prev` 必须等于当前链头（拒绝不属于本谱系的 WAL）。

`Verify()` / `VerifyDir()` 为只读校验；若发现比清单更新的 WAL，返回 `ErrWALUncommitted`（提示调用 `Recover()`），不擅自改写。`Recover()` 显式重放并重载内存数据库。

### 2.4 备份轮转（需求 3）

- `backups/snapshot-%020d.json`（seq 补零，字典序即时间序），内容为标准快照文档，权限 0600，目录 0700。
- 每次提交后 `rotateBackups(dir, canonical, seq, retain)` 按名称排序删除最旧份，只保留最近 N 份；默认 `N=5`，`SetBackupRetention(n)` 可设 1..100，`Options.BackupRetention` 可配置。
- `Backup()` 可随时为当前已提交状态额外生成一份并轮转。

### 2.5 并发与竞态消除（需求 4）

- `Store` 新增 `writeMu sync.Mutex`：**所有落盘写路径**（`Save` / `WAL` / 表文件 / 清单 / 备份 / 轮转 / `Recover` / `Backup` / `SetBackupRetention` / `HardenPermissions`）全部串行化。
- 原有 `mu sync.RWMutex` 继续保护 `db` 与全部内存索引；`saveHardened()` 在 `mu.RLock()` 下构建快照，随后释放锁再写盘，写盘期间其它 goroutine 的 `Lock()` 会被 `RLock()` 阻塞，保证快照一致性。
- `manifest / opts / status` 三个新字段由 `writeMu` 保护；`IntegrityStatus()` 亦在 `writeMu` 下读取。
- 既有写方法（`CreateUser`、`AdjustQuota`、`ApplyBilling`、`UpdateChannelLocked`、`SetPasswordHash`、`AddUsage`、`SetSetting` …）已全部持 `mu.Lock()`，未改动。
- `go test -race ./src/internal/store/` 真实通过（见 §4）。

### 2.6 字段级加密与口令哈希（需求 5）

- `Channel.APIKeyCipher / APIKeyIV / APIKeyTag` 仍为 `[]byte`，Go `encoding/json` 自动 base64 落库；`KeyHint` 仍只存脱敏提示。**本加固不解密、不改动、不回显任何明文**。
- `User.PasswordHash` 原样持久化（迭代哈希由 `crypto` 包负责，store 不触碰）。
- 真实测试 `TestFieldEncryptionAndPasswordHashUnchanged`：断言状态文件中不含 `sk-super-secret-upstream-key` 明文、含 base64 密文与 `key_hint`、口令哈希逐字不变、重开后三段密文逐字还原。
- 表文件编码仍为 `json.MarshalIndent(..., "", "  ")`，与加固前一致，其它团队读取方式不变。

### 2.7 兼容性与新增 API

**全部既有导出类型/函数签名未变**（`New(dir) (*Store, error)`、`Save() error`、10 个实体类型、`Counts`、全部 CRUD、`ApplyBilling`、`UpdateChannelLocked`、`SetPasswordHash` 等逐字保留）；`New`/`Save` 仅改函数体委托到新实现。

| 新增 | 用途 |
|---|---|
| `type Options` / `DefaultOptions()` / `NewWithOptions(dir, opts)` | 可配置备份份数、`Strict` 严格模式、`DisableWAL` |
| `type IntegrityError` / `IsIntegrityError(err)` | 明确的篡改错误类型 |
| `type IntegrityStatus` / `(*Store) IntegrityStatus()` | 序列/链长/链头/备份数/是否恢复/是否采纳遗留数据 |

按任务要求「不改任何其它目录」，本团队未修改 `tests/`、`auth/`、`middleware/`；这 3 个失败需由对应团队自行对齐测试契约。
