# 21 · 反代理上游接入指南（ChatGPT / Claude / Gemini / xAI / workbuddy / qoder）

> 天衡是「众包渠道 + 统一出口」的聚合站：任何登录用户在 `/channels` 页填 **渠道类型 + base_uri + api_key** 三个字段，站点就会自动 `GET {base_uri}/models` 拉取该上游的**全部真实模型**并入库——不需要填写任何模型。之后任何人用 `/tokens` 生成的 `sk-` 令牌，通过统一的 `/v1/chat/completions`（OpenAI 协议）即可调用所有渠道的模型；协议差异由天衡的适配器层双向转换。

## 0. 三步接入（对全部上游通用）

```
1. 登录天衡 → 打开「渠道」页（/channels）
2. 填三个字段：provider_type（渠道类型）、base_uri（上游地址）、api_key（上游密钥）
3. 提交 → 站点自动发现该上游全部真实模型 → 立即可用
```

用户不需要填模型列表、不需要填路径、不需要了解上游协议——类型选对，其余全自动。

## 1. 各上游的真实接入参数

### ChatGPT（OpenAI）

| 字段 | 值 |
|---|---|
| `provider_type` | `openai` |
| `base_uri` | `https://api.openai.com/v1` |
| `api_key` | `sk-…`（OpenAI 平台密钥） |

- 适配器：`OpenAICompatAdapter`（透传，保留 `reasoning_content` 等差异字段）
- 鉴权：`Authorization: Bearer <key>`
- 路径：`GET /models`、`POST /chat/completions`（默认，可省）

### Claude（Anthropic）

| 字段 | 值 |
|---|---|
| `provider_type` | `anthropic` |
| `base_uri` | `https://api.anthropic.com/v1` |
| `api_key` | `sk-ant-…`（Anthropic 控制台密钥） |

- 适配器：`AnthropicAdapter`（**双向协议转换**：OpenAI ⇄ Anthropic）
- 鉴权：`x-api-key: <key>` + `anthropic-version: 2023-06-01`（适配器自动加）
- 路径：`GET /models`、`POST /messages`
- 调用方式不变：客户端仍然发 OpenAI 协议到 `/v1/chat/completions`，天衡转成 Anthropic 协议发给上游，再把响应转回 OpenAI 协议
- 真实验证：`docs/20` 同款流程已用 Anthropic 协议 mock 上游端到端跑通——OpenAI 协议进 `{"model":"claude-haiku-5.5",…}` → 上游收到 `/messages` 形状 → 响应转回 `choices[].message.content`，usage 逐字段换算

### Gemini（Google）

| 字段 | 值 |
|---|---|
| `provider_type` | `gemini` |
| `base_uri` | `https://generativelanguage.googleapis.com/v1beta/openai` |
| `api_key` | `AIza…`（Google AI Studio 密钥） |

- 适配器：`GeminiAdapter`（走 Google 官方的 **OpenAI 兼容层**，保证聚合出口一致）
- 鉴权：`Authorization: Bearer <key>`
- 路径：`GET /models`、`POST /chat/completions`（Google 兼容层提供）
- 注意：`base_uri` 必须带 `/v1beta/openai`（兼容层入口）；原生 `generateContent` 由 Google 的兼容层代为适配

### xAI Grok

| 字段 | 值 |
|---|---|
| `provider_type` | `xai` |
| `base_uri` | `https://api.x.ai/v1` |
| `api_key` | `xai-…` |

- 适配器：OpenAI 兼容（保留 grok 的 `reasoning_content`、`live_search` 差异字段）
- 鉴权：`Authorization: Bearer <key>`

### workbuddy / qoder / 其它订阅型平台（OpenAI 兼容的都走这里）

这类平台提供 OpenAI 兼容端点，用 `openai_compatible` 类型接入：

| 字段 | 值 |
|---|---|
| `provider_type` | `openai_compatible` |
| `base_uri` | 平台文档给的 OpenAI 兼容地址（例：`https://<平台域名>/v1`） |
| `api_key` | 平台发放的令牌 |

- 适配器：`OpenAICompatibleAdapter`——**支持路径与请求头全覆盖**：
  - `models_path`（上游模型列表不在 `/models` 时）
  - `chat_path`（对话端点不在 `/chat/completions` 时）
  - `auth_style`：`bearer`（默认）或 `x-api-key`
  - `custom_headers`：平台要求附加的请求头（禁止覆盖鉴权/传输头，防头注入）
- 接入步骤：在该平台拿到「API 端点 + 令牌」→ 如果端点是 OpenAI 兼容形状就填上；路径不同就补 `models_path` / `chat_path`

```
POST /api/channels
{
  "name": "workbuddy",
  "provider_type": "openai_compatible",
  "base_uri": "https://<workbuddy 端点>/v1",
  "api_key": "<workbuddy 发放的令牌>"
}
```

## 2. 提交之后发生了什么（全自动）

```
POST /api/channels
   ↓ SSRF 校验（仅 http/https，拒绝内网/回环/元数据）
   ↓ AES-256-GCM 加密 api_key（库内只存密文 + key_hint 末4位）
   ↓ 真实 GET {base_uri}/models → 拉取全部真实模型
   ↓ 逐模型入库（id/参数/价格/capability 位）
   ↓ （可选）真实探测：发一次极小请求采集输入输出样例
   ↓ 分组自动派生：auto/model/<真实id>（零配置，见 docs/20）
```

拉取失败 → `probe_status=unavailable`，**列表为空，绝不编造模型**。

## 3. 调用（对所有上游统一）

```bash
# 生成平台令牌（只需 name，无任何限制字段）
curl -X POST $H/api/tokens -H "Authorization: Bearer $JWT" \
  -H 'Content-Type: application/json' -d '{"name":"my"}'

# 用返回的 sk- 调任何渠道的模型（统一 OpenAI 协议）
curl $H/v1/chat/completions \
  -H "Authorization: Bearer sk-…" -H 'Content-Type: application/json' \
  -d '{"model":"claude-haiku-5.5","messages":[{"role":"user","content":"你好"}]}'
```

请求进入后（真实链路，见 docs/20）：

```
分组解析（自动分组 + 条件规则）
→ 会话亲和（多轮对话钉住同一上游，复用 prompt 缓存）
→ 出站脱敏（三级：known/model/rule × 11 类，遮蔽后发出）
→ 协议转换（按 provider_type 适配）
→ 失败切换（MAX_FAILOVER 内逐候选尝试）
→ 响应转回 OpenAI 协议 + 入站还原脱敏占位符
→ 决策留痕（order/tries/affinity/masking/prompt）
```

## 4. 多渠道聚合：同名模型自动负载均衡

同一真实模型出现在多个渠道（例如两家供应商都有 `claude-haiku-5.5`）时：

- 自动分组 `auto/model/claude-haiku-5.5` 把两个渠道聚齐
- 每次调用按**权重 + 优先级 + 最少在途**选择渠道，失败自动切换
- 多轮会话粘住同一渠道保缓存（亲和）
- 贡献渠道的拥有者按 `CONTRIBUTOR_REWARD_RATE` 获得记账奖励

## 5. 鉴权头速查（适配器自动处理）

| provider_type | 鉴权头 | 版本头 | 对话路径 |
|---|---|---|---|
| `openai` | `Authorization: Bearer` | — | `/chat/completions` |
| `anthropic` | `x-api-key` | `anthropic-version: 2023-06-01` | `/messages` |
| `gemini` | `Authorization: Bearer` | — | `/chat/completions`（Google 兼容层） |
| `xai` | `Authorization: Bearer` | — | `/chat/completions` |
| `openai_compatible` | Bearer 或 `x-api-key`（`auth_style` 可选） | 自定义 | 自定义（`chat_path`） |

## 6. 安全边界（为什么这么设计）

- **SSRF 防护**：`base_uri` 只允许 http/https；拨号前解析并校验每个 IP，拒绝内网/回环/元数据地址；重定向每跳重校验（生产默认开启；本机联调设 `ALLOW_PRIVATE_UPSTREAM=1` 放行，生产绝不设）
- **密钥只存密文**：AES-256-GCM，库内只有密文与 `key_hint`（末 4 位）；日志与错误体经脱敏
- **出站脱敏**：转发给第三方上游前，把请求里的密钥/IP/家目录/邮箱等替换成占位符，响应回来再还原（docs/20 原理③）
- **自定义头白名单**：`custom_headers` 不能覆盖 `Authorization` / `Content-Type` 等关键头，不能含 CR/LF/NUL
