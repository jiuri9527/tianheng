## 2. 发现的漏洞（本轮新增 3 条）

### V-36 [High] CWE-284 / CWE-770 — 自动保护解锁通道可被攻击者即时解除

- **证据**：修复前 `src/internal/api/firewall_api.go:35-49`（任意 JWT 持有者即可 `Unlock`）；`src/internal/firewall/firewall.go:378-383`（`unlockPath` 在 lockdown/封禁分支对非回环同样放行）。
- **触发路径（靶场真实复现）**：攻击者注入 → `FW_AFTER: level=lockdown sealed=True` → 全站 423 → 攻击者用自己的 JWT `POST /api/firewall/unlock` → 立即解除 → 再次注入，循环。自动保护被武器化成**持久 DoS 开关**，"攻击时自动保护"承诺失效。
- **修复**（`patches/019-firewall-ops-loopback-only.patch`，已应用）：unlock/seal 仅接受本机回环来源（`opsIsLoopback`），远程一律 403 `ops_loopback_only`。解锁是攻防开关而非业务能力，与"全员超级用户"的业务语义不冲突。
- **复测**：`tests/superuser_test.go` 用 `RemoteAddr=192.0.2.1`（非回环）真实断言 seal 403、回环 200（`doLoopback` helper）；靶场（本机即回环）`LOOPBACK_SEAL=200 → STATUS: lockdown sealed=True → BIZ_DURING_SEAL=423 → LOOPBACK_UNLOCK=200 → 业务恢复`。`TestAllUsersAreSuperusers` PASS。

### V-38 [High] CWE-770 — 封存期间认证端点全封造成「自锁 DoS」

- **发现过程（真实）**：dir_scan 扫描触发 auto_lockdown 后，靶场上 `POST /api/auth/login` 与 `/api/auth/register` 均返回 `{"code":"firewall_lockdown"}`（423）→ 运维若未在攻击前持有 JWT，则**永远无法登录再解锁**：攻击者一次注入即可把站点打成「封存态永久自锁」，即使冷却到期 level 降级，`sealed` 仍需显式解锁，而解锁需要 JWT，JWT 需要登录，登录被封存阻断 —— 死循环。
- **证据**：`src/internal/firewall/firewall.go`（修复前）`allowOps` 仅放行 `/healthz`、回环防火墙状态端点与 unlock 路径；`/api/auth/login|register|refresh` 在 `sealed` 分支被一律 423；靶场实测 `SEALED_LOGIN_HEAD={"error":{"code":"firewall_lockdown"}}`。
- **修复**（`patches/021-firewall-sealed-auth-recovery-loopback.patch`，已应用）：`authRecovery` 回环专用恢复通道 —— login/register/refresh **仅对本机回环**放行；远程攻击者仍然完全无法在封存期间认证（保护语义不变），本机运维随时可登录再解锁。
- **复测（靶场 18400 真实序列）**：
```
ATTACK_/.env=404 → STATUS: lockdown sealed=True epoch=1   （/.env 触发 state_probe）
SEALED_REGISTER=200  SEALED_LOGIN=200（回环恢复通道）JWT_LEN=224
SEALED_UNLOCK=200 → RESTORED: observe sealed=False → BIZ_RECOVERED=200
```
单测 `TestSealedAuthRecoveryLoopbackOnly`：远程 login 封存期间 423、回环 200，PASS。

### V-37 [Medium] CWE-400 — telemetry SSE 无并发上限 + 每连接独立全量聚合

- **证据**：`src/internal/telemetry/telemetry.go`（修复前）`stream()` 无连接计数；`writeFrame()` 每连接每 2s 各自调 `aggregate(h.st, …)` 全量扫描 request_logs。N 个恶意连接 = 每 2s N 次全量聚合 + N 个常驻 goroutine，单机即可资源耗尽。
- **修复**（`patches/020-telemetry-stream-cap-and-shared-snapshot.patch`，已应用）：① 全局 `streamConns atomic.Int64`，默认 256 并发流上限（`TELEMETRY_STREAM_MAX_CONNS` 可覆盖），超限 503 `too_many_streams`；② `cachedAggregate` 让同一 interval 内所有连接共享同一份聚合结果（每 tick 只算一次）。
- **复测（真实原始 socket 保持打开）**：300 并发保持流 → `{'200': 256, '503': 44}` → **PASS（超出 256 的流被拒绝）**。
